# inbox — вход для задач и багов из Obsidian

Сюда Obsidian кладёт заметки, отсюда их раз в неделю, по понедельникам
в 09:00 МСК, разбирает автоматика (навык `/inbox`, Routine «Canary — разбор
inbox»). Баги чинятся кодом в отдельной ветке, под задачи пишутся краткие
пути реализации — сами задачи автоматика не делает. Отчёт возвращается
в `reports/` тем же git-ом и виден в Obsidian, плюс приходит пушем и письмом.

## Папки

| Папка | Что лежит |
|---|---|
| `tasks/` | задачи: под каждую прогон пишет «Пути реализации», код не трогает |
| `bugs/` | баги: прогон чинит кодом |
| `done/` | починенное — сюда файл переезжает сам |
| `reports/` | отчёт за прогон, `ГГГГ-ММ-ДД.md` |
| `_templates/` | шаблоны для Obsidian Templater |
| `attachments/` | скриншоты из заметок |
| `*.md` в корне | твои заметки из хранилища (`Таски.md` и что ещё напишешь); строки `- [ ]` в них становятся задачами. Единственное, что прогон в них меняет, — ставит `[x]` и ссылку `[[done/…]]` за починенное |
| `Багфиксы.md` или папка `Багфиксы/` | строки `- [ ]` отсюда становятся багами, не задачами. Признак — слово «баг» в имени файла или папки; раздел `## Баги` внутри любой заметки работает так же |
| `Мои задачи.md` | личный список — помечен `canary: ignore`, разбор его не читает |
| `Личное/` (только в хранилище) | остаётся на маке: в репозиторий не копируется вовсе |

## Два способа поставить задачу

**Обычной заметкой.** Пишешь с телефона как пишешь — списком с галочками.
`tools/inbox-extract.py` берёт каждую строку `- [ ]` и заводит под неё заметку,
один раз на строку (помнит в `.extracted.json`). Куда — решает слово «баг»:
строка из `Багфиксы.md`, из папки `Багфиксы/` или из-под заголовка `## Баги`
едет в `bugs/` и будет починена кодом; всё остальное — в `tasks/`, и под неё
прогон напишет только пути реализации. Этого хватает в большинстве случаев.

**Никак** — если заметка не для разбора. Шапка из трёх строк в начале файла:

```markdown
---
canary: ignore
---
```

и галочки из неё задачами не станут. Так сделан `Мои задачи.md`; пометить
можно любую заметку, и переименование её не расколдует. Пустая `- [ ]` —
заготовка, а не задача, её извлечение пропускает и без пометки.

**Совсем мимо репозитория** — папка `Личное` в хранилище. Синхронизация её
не копирует, поэтому в git она не попадает ни при каком раскладе, а репозиторий
публичный. Туда — недодуманное, адреса стендов, что угодно. Папка заводится
сама при первом прогоне синхронизации, вместе с `Черновик.md`.

Разница с `canary: ignore` простая: помеченная заметка в репозитории лежит,
просто не разбирается; папка `Личное` до репозитория не доезжает вовсе.

**Отдельной заметкой по шаблону** — когда у бага есть шаги воспроизведения
и известно, где он живёт. `scope` сужает поиск. Формат ниже.

## Формат заметки

Фронтматтер обязателен: по нему автоматика решает, брать файл или нет.
Заметка без `status` не берётся вовсе — это защита от черновика, случайно
попавшего в папку.

```markdown
---
status: todo
kind: bug
scope: AppMVP/Core/Pure/ServiceMath.swift
---

Остаток до ТО считается от одометра, а не от пробега на момент последнего ТО:
после замены масла на 150 000 «ТО через» показывает 10 000 вместо 15 000.

## Как воспроизвести
1. Завести машину с пробегом 150 000.
2. Отметить замену масла.
3. Главный экран: «ТО через 10 000 км».
```

### Поля

- **`status`** — `todo` (взять в работу), `doing`, `done`, `blocked`,
  `needs-review` (правка сделана, но проверить может только человек),
  `duplicate` (уже сделано в другой ветке — ставит `tools/inbox-dedup.py`).
  Автоматика берёт **только `todo`**.
- **`kind`** — `bug` или `task`. Это главное поле: баг чинится кодом,
  задача получает только «Пути реализации».
- **`scope`** *(необязательно)* — путь к файлу или папке. Сужает поиск и
  экономит время прогона.
- **`priority`** *(необязательно)* — `high` берётся первым.

## Что автоматика делает сама

**Баги чинит кодом** — включая вью. Xcode в облаке нет, поэтому правка едет
в ветку с пометкой «сборкой и сверкой с макетом не проверено»: собираешь
и смотришь ты. Не воспроизвёлся по коду — `blocked` и строка, чего не хватает.

**Под задачи пишет пути реализации** — два-три пути в заметку, по строке-две
на каждый, и какой разумнее. Код не трогает, заметка остаётся в `tasks/`
со `status: needs-review`. Решил делать — скажи в сессии Claude, с какого
пути начинать.

**Починенное отмечает сам.** После закрытия бага `tools/inbox-close.py` находит
исходную строку в твоей заметке и ставит `- [x] … — [[done/имя]]`: галочка
и ссылка на заметку, где лежат «Что сделано» и имя ветки. Ничего другого
в твоём тексте он не меняет. Тест: `tools/inbox-close-test.sh`.

**Дважды одну работу не делает.** Перед разбором `tools/inbox-dedup.py`
сверяет каждую `todo` с `done/` во всех ветках на GitHub: закрыто хоть где-то —
заметка получает `status: duplicate` и в очередь не идёт. Ключ — текст первой
строки, так что переименование файла не спасает от проверки и не ломает её.
Тест: `tools/inbox-dedup-test.sh`, гоняется на отдельном репозитории.

Проверяется тем, что работает без Xcode:

- логика в `AppMVP/Core/Pure/` — её накрывает `./tools/run-pure-checks.sh`;
- русская типографика в строках — `tools/check-typography.py`;
- документы в `docs/`;
- скрипты в `tools/`.

Баг вне кода проекта (сервер, чужой сервис) и всё, что сидит
в `Canary.xcodeproj`, только разбирается: ручной файл проекта ломается молча,
и вслепую его не трогают.

## Куда уходят правки

Ветка `claude/inbox-ГГГГ-ММ-ДД`, один коммит на заметку. `main` не трогается,
PR автоматика не открывает — сливаешь сам, посмотрев диф.

## Как это связать с Obsidian

**Заметки на GitHub относит мак, а не телефон.** Пишешь с телефона в папке
`canary` своего хранилища, Obsidian синхронизирует её на мак, а там раз в день
`tools/inbox-sync.sh` переносит заметки в `inbox/` и пушит. Разбор в облаке
видит только GitHub — телефон ему недоступен. Синхронизация остаётся
ежедневной, хотя разбор недельный: заметки уезжают в git сразу, а отчёт
понедельника возвращается в хранилище тем же утром.

Установка на маке, один раз:

```bash
# заполнить REPO и VAULT в начале скрипта
chmod +x tools/inbox-sync.sh
tools/inbox-sync.sh                     # разовый прогон: проверить, что пути верны
cp tools/dev.canary.inbox-sync.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/dev.canary.inbox-sync.plist
```

Скрипт ходит в обе стороны: заметки из хранилища едут в репозиторий, а оттуда
зеркалом возвращаются `done/` и `reports/` — разобранная заметка исчезает
из `bugs/` на телефоне, и следующий разбор не берёт её снова. Запуск —
в 08:45, в 09:30 и при входе в систему. Мак спал — launchd догоняет после
пробуждения. Журнал: `/tmp/canary-inbox-sync.log`.

**Скриншоты.** В Obsidian: Настройки → «Файлы и ссылки» → папка для вложений →
`attachments` внутри `canary`. Тогда картинка из заметки доедет вместе с ней,
и разбор её откроет.

**Почему не плагин Git прямо на телефоне.** Репозиторий весит 85 МБ истории
и 71 МБ картинок в `AppMVP/`. Плагин на мобиле — это git, переписанный на JS;
такой клон он либо не вытянет, либо будет тянуть при каждом старте. На маке
это обычный `git` и обычный `rsync`.

**Симлинком тоже не получится.** Если хранилище лежит отдельно и внутри него
симлинк на `inbox/`, git хранит симлинк ссылкой и внутрь не заходит — заметки
не попадают ни в один коммит, а выясняется это утром на пустой очереди при
полной папке.

Проверить, что связь работает: написать заметку с телефона, дождаться
синхронизации Obsidian, запустить `tools/inbox-sync.sh` руками и посмотреть
`python3 tools/inbox-scan.py` — заметка должна оказаться в очереди.
