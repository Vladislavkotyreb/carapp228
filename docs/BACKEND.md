# Хранение данных и будущий бэкенд

## Где данные сейчас

**Только на устройстве.** Машины, история ТО и приложенные чеки лежат в
SwiftData — модели `AppMVP/Models/Car.swift` и `ServiceRecord.swift`,
контейнер подключается в `AppMVP/App/AppMVPApp.swift`. Ничего никуда не
передаётся.

Supabase удалён: он хостится за пределами РФ, а приложение делается для
российских пользователей. Заодно выяснилось, что в приложении он был
нерабочим каркасом от шаблона — экраны `Login`/`SignUp`/`Home`/`Profile`
были недостижимы из `RootView`, а схема на сервере содержала таблицы
`profiles` и `items (title text)`, не имеющие отношения к машинам.

Пока данные не покидают телефон, обязанностей оператора персональных данных
по 152-ФЗ не возникает. Они появятся вместе с сервером.

## Главное правило будущего сервера

**Приложение не должно подключаться к базе напрямую.**

Строка подключения, зашитая в приложение, достаётся из `.ipa` за несколько
минут: файл распаковывается как обычный архив, строки вынимаются из бинарника.
Дальше любой человек получает полный доступ к базе всех пользователей —
чтение, изменение, удаление. Никакие обфускации это не лечат: ключ, который
есть у приложения, есть и у того, кто его разобрал.

Поэтому между приложением и базой обязателен HTTP API: он живёт на сервере,
знает пароль от базы, а приложению выдаёт только короткоживущий токен своего
пользователя. Supabase позволял ходить «напрямую» лишь потому, что у него
поверх базы стоит слой Row Level Security и проверка JWT — то есть тот же API,
просто готовый. У голой БД на VPS такого слоя нет.

## Что нужно от сервера

Посмотрите в панели ISPmanager и пришлите:

- [ ] тип и версия СУБД — MySQL/MariaDB или PostgreSQL
- [ ] есть ли доступ по SSH и права root
- [ ] привязанный домен и есть ли TLS-сертификат (Let's Encrypt подойдёт)
- [ ] **страна, где физически стоит сервер** — для 152-ФЗ это ключевое
- [ ] доступные версии PHP / Python / Node.js

От этого зависит, на чём писать API. Без SSH останется PHP — он на таком
хостинге есть всегда.

## Эскиз API

Под текущие экраны приложения:

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/phone/request` | отправить код на телефон |
| `POST` | `/auth/phone/verify` | проверить код, выдать токены |
| `POST` | `/auth/apple` | проверить `identityToken` Apple, привязать аккаунт |
| `POST` | `/auth/refresh` | обновить access-токен |
| `GET` | `/cars` | список машин пользователя |
| `POST` | `/cars` | добавить машину |
| `PATCH` | `/cars/{id}` | обновить пробег и данные |
| `DELETE` | `/cars/{id}` | удалить машину вместе с историей ТО |
| `GET` | `/cars/{id}/services` | история ТО |
| `POST` | `/cars/{id}/services` | добавить ТО с работами |
| `POST` | `/uploads` | фото машины и чеки |

Вход по телефону с кодом требует платного SMS-шлюза и **нового экрана,
которого нет в макете** — его нужно будет нарисовать. Кнопка «Войти с Apple»
в онбординге уже стоит, но сейчас ничего не делает: обработчик в
`OnboardingView.handleAppleSignIn` просто продолжает флоу. Проверку токена
делает сервер, в базе в РФ лежит только наша запись о пользователе.

## Что понадобится по 152-ФЗ

Техническая часть, которую делаю я:

- база физически в РФ;
- HTTPS на всех запросах, без исключений;
- пароли и коды — только в виде хешей, никогда в открытом виде;
- журнал доступа к персональным данным;
- экран согласия на обработку до начала сбора данных;
- удаление аккаунта вместе со всеми данными по запросу пользователя;
- резервные копии тоже в РФ.

Организационная часть — на вас с юристом, я тут не советчик:

- уведомление Роскомнадзора о начале обработки персональных данных;
- политика обработки персональных данных, опубликованная и доступная
  из приложения (Apple также требует ссылку на неё при публикации);
- определение уровня защищённости по постановлению правительства № 1119
  и мер защиты по приказу ФСТЭК № 21;
- порядок уведомления РКН об утечках.

Отдельно учтите: **госномер и VIN считаются персональными данными**, когда их
можно связать с человеком. То есть 152-ФЗ распространяется на Beepy, даже если
не собирать ФИО.
